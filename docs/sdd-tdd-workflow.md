# 「先 SDD，再 TDD」开发流程

> 关联 Issue：#4
> 状态：流程倡议（Proposal）

本仓库的日常开发采用 **「先 SDD（规范驱动开发），再 TDD（测试驱动开发）」** 的协作流程：先用规范（Spec）把"做什么、做到什么程度算完成"写清楚，再用测试把规范落地为可执行的红-绿-重构循环。

## 核心理念

### 第一步：SDD —— Specification-Driven Development（规范驱动开发）

先写规范，后写代码。规范至少包含：

- **需求描述**：要解决什么问题、面向什么场景；
- **输入 / 输出契约**：接口、数据格式、边界条件（例如 `scripts/ai_daily.py` 的输入来源、输出到 `ai-daily/YYYY-MM-DD.md` 的格式约定）；
- **验收标准**：可判定的完成条件（DoD），避免"差不多就行"；
- **非目标**：明确本期不做什么，防止范围蔓延。

规范应提交进仓库（如 `docs/spec/` 或随功能目录放置），与代码同评审、同演进。

### 第二步：TDD —— Test-Driven Development（测试驱动开发）

规范评审通过后，进入红-绿-重构循环：

1. **红（Red）**：把规范中的一条验收标准转成一个失败测试；
2. **绿（Green）**：写最少实现让测试通过；
3. **重构（Refactor）**：在测试保护下清理代码，规范不变、测试不破。

重复直至覆盖规范中的全部验收标准。

## 为什么是这个顺序

- **SDD 回答"做什么 / 为什么"**，TDD 回答"怎么证明做对了"；没有规范支撑的测试容易退化成"为实现而测"，锁死错误设计；
- 规范先行让测试天然具备可追溯性：每个测试都能指回一条验收标准；
- 评审前置：规范比代码便宜，返工成本最低的阶段就发现问题。

## 落地路线

- [ ] 建立 `docs/spec/` 目录与规范模板（背景 / 契约 / 验收标准 / 非目标）；
- [ ] 以 `scripts/ai_daily.py` 为试点：先补一份收集规则的规范，再按其补单元测试（去重 `seen.json`、来源失败降级、同日跳过等现有行为）；
- [ ] PR 模板增加一节「关联规范 + 覆盖的验收标准」；
- [ ] CI（`.github/workflows/`）中对带测试的模块运行测试套件；
- [ ] 约定：无规范不开工，无测试不合入。

## 备注

本文档为流程倡议，不涉及具体代码改动；如认可该方向，可把上方清单拆成子任务逐项推进。
